# Fallout 1 场景地图渲染设计与实践

## 目标与边界

本阶段把已结构化的 `.MAP` 数据与原始 FRM 合成为可查看的 PNG。首个样板是哈勃旧城区 `HUBOLDTN`：已依次完成地面、墙壁、门、非门场景物件、物品及人物与生物的独立层和合成图；屋顶、光照和脚本状态分阶段加入。游戏安装目录、提取后的 `.MAP`、`.FRM`、`.PAL` 和既有 JSON 均作为只读输入，新产物固定写入 `workspace/output/maps-rendered/`。

“完整地图”需要区分三个层次：

1. 地面底图：每个楼层的 100×100 个方形地砖。
2. 静态场景图：地面、屋顶及按深度排序的墙体和物件。
3. 游戏时态图：再考虑门的开关、人物帧、脚本改变和屋顶遮挡。离线渲染首先追求前两层，不执行游戏脚本。

## 数据链路

- `workspace/output/maps/<source>/MAPS/<name>/<name>.json`：楼层、打包地砖、对象和脚本。
- `workspace/raw/master/ART/TILES/TILES.LST`：地砖 FID 低位编号到 FRM 文件名的零基映射。
- `workspace/raw/master/ART/TILES/*.FRM`：调色板索引像素；0 号颜色透明。
- `workspace/raw/master/ART/WALLS/WALLS.LST`：墙壁 FID 低 12 位到 FRM 文件名的零基映射。
- `workspace/raw/master/ART/WALLS/*.FRM`：墙壁各方向、帧和方向锚点偏移。
- `workspace/raw/master/ART/SCENERY/SCENERY.LST`：场景 FID 低 12 位到 FRM 文件名的零基映射。
- `workspace/raw/master/ART/SCENERY/*.FRM`：门及其他场景物件的方向和动画帧。
- `workspace/raw/master/ART/ITEMS/ITEMS.LST`：物品 FID 低 12 位到 FRM 文件名的零基映射。
- `workspace/raw/master/ART/ITEMS/*.FRM`：容器、武器和其他地图顶层物品的方向与动画帧。
- `workspace/raw/critter/ART/CRITTERS/CRITTERS.LST`：人物与生物 FID 低 12 位到基础造型名及特殊动画别名的映射。
- `workspace/raw/critter/ART/CRITTERS/*.{FRM,FR0…FR5}`：由基础造型、武器姿态和动作代码共同命名的人物动画；大型动画可能按方向拆分。
- `workspace/raw/master/TEXT/ENGLISH/GAME/PRO_CRIT.MSG`：人物原型显示名，消息号为原型零基索引乘 100。
- `config/huboldtn-critter-names.zh-CN.json`：提取名称到中文名称的显式映射、少数复用通用原型人物的脚本名覆盖，以及需要中英文双语显示的专名名单。
- `workspace/raw/master/TEXT/ENGLISH/GAME/PRO_ITEM.MSG`：物品原型显示名，同样以原型零基索引乘 100 作为消息号。
- `config/huboldtn-item-names.zh-CN.json`：HUBOLDTN 顶层物品及其容器库存所需的中文名称显式映射。
- `workspace/raw/master/COLOR.PAL`：Fallout 主调色板。

渲染器验证 JSON 结构、数组长度、地砖编号范围和所有输入文件，再进行任何写入。默认 dry-run，只有 `--execute` 才原子生成 PNG、元数据 JSON 和校验文件。

## 坐标与绘制顺序

地图保存 100×100 个方形地砖。对存储索引 `i`：

```text
column = 99 - (i mod 100)
row    = i div 100
screen_x = 48 × column + 32 × row
screen_y = -12 × column + 24 × row
```

该公式对应 Fallout Community Edition 固定提交 `0609bcf` 的 `square_coord`。地面按存储行、再按列递增绘制，与 `square_render_floor` 一致。地砖标志最低位为 1 时跳过；地砖编号取打包值低 12 位。画布边界由实际包含非透明像素的地砖帧计算，最后平移到非负坐标，避免保留无意义的大块透明区域。

参考：[`tile.cc`](https://github.com/alexbatalov/fallout1-ce/blob/0609bcfd0ec40ff0571d0f57fab2821eb461dc8b/src/game/tile.cc)。

墙壁附着在 200×200 六角格上。渲染器先把六角格换算到与地面相同的全局坐标，再按游戏对象锚点定位：

```text
anchor_x = hex_x + 16 + direction_x_offset + object_x
anchor_y = hex_y + 8  + direction_y_offset + object_y
left = anchor_x - frame_width div 2
top  = anchor_y - (frame_height - 1)
```

墙体 FID 类型必须为 3，低 12 位作为 `WALLS.LST` 的零基索引；跳过 `OBJECT_HIDDEN`。绘制顺序复现 `obj_render_pre_roof`：先按六角格编号递增绘制带 `OBJECT_FLAT` 的墙，再按相同顺序绘制普通墙；同格对象保留 MAP 中的先后次序。首轮不模拟玩家周围的半透明“蛋形”遮挡，也不应用环境光，便于单独验证素材、坐标和遮挡。

参考：[`object.cc`](https://github.com/alexbatalov/fallout1-ce/blob/0609bcfd0ec40ff0571d0f57fab2821eb461dc8b/src/game/object.cc)、[`object_types.h`](https://github.com/alexbatalov/fallout1-ce/blob/0609bcfd0ec40ff0571d0f57fab2821eb461dc8b/src/game/object_types.h)。

门通过原型 `type=scenery, subtype=door` 识别，FID 类型必须为 2。门与墙体使用相同的六角格锚点公式，但读取 `SCENERY.LST` 和对象保存的方向、帧。游戏以 `frame == 0` 判断关闭，非零帧表示打开或动画中；`update_data.open_flags` 的最低位记录目标开门状态，另外 `0x02000000` 和 `0x04000000` 分别表示锁定、卡住。离线静态图严格渲染 MAP 保存帧，不自行开门或执行脚本。

非门场景物件同样使用 `SCENERY.LST`：目前包括 `stairs`、`elevator`、`ladder_up`、`ladder_down` 与 `generic` 原型。它们沿用门的 FID、方向、帧、像素偏移和锚点校验，但不读取门状态。场景物件透明层只绘制这些非门对象；最终合成把墙、门和非门场景物件统一排序，依旧先 `OBJECT_FLAT`，再普通对象，并以六角格编号与 MAP 源顺序稳定打破并列。

地图顶层物品的 FID 类型为 0，使用 `ITEMS.LST` 和相同的六角格锚点公式。物品独立层包括容器、武器和其他直接放置在地图上的物品；容器或人物 `inventory` 中嵌套保存的物品只在元数据中计数，不作为地面对象绘制。最终合成把物品与墙、门、场景物件放入同一排序队列，以保留跨类型遮挡关系。

物品通常与家具融为一体，完整地图缩放后难以辨认，因此物品阶段同时输出 `elevation-<n>-floor-walls-doors-scenery-items-highlighted.png`。高亮图在每个物品的非透明像素外围绘制 2 像素黄色轮廓，再保留物品原始像素；颜色从 Fallout 主调色板中选择最接近亮黄色的非透明索引。原始物品层和无描边合成图保持不变，可分别用于素材核对和正常地图展示。

人物与生物的 FID 类型为 1。低 12 位选择 `CRITTERS.LST` 的基础造型，位 12–15 表示武器动画类型，位 16–23 表示动作，位 28–30 在大型死亡动画中选择 `.FR0`–`.FR5` 分方向文件。渲染器按游戏 `art_get_code` 的规则生成两位文件代码，而不是直接把 FID 数字转换成字母；特殊死亡动作还会应用 `CRITTERS.LST` 中记录的造型别名。组合 FRM 使用 MAP 保存的 rotation，分方向 FRM 使用文件自身的方向锚点，最后仍套用相同的六角格对象锚点公式。

人物阶段表达的是 MAP 静态快照：保存的 FID、方向、帧和像素偏移会被保留，但不执行移动、循环动画、AI、人物脚本或光照，也不会加入通常由运行时创建的玩家角色。人物透明层、无描边完整合成图之外，还生成 `elevation-<n>-floor-walls-doors-scenery-items-critters-highlighted.png`：用 2 像素黄色轮廓标出每个顶层物品，同时用 2 像素亮绿色轮廓标出每个可见人物或生物。两类对象共享保护掩码，轮廓不会盖住物品或人物自身的原始像素。原始发行资源缺失某个人物 FRM 时，元数据记录对象、脚本名和应有文件名并跳过绘制，不拿其他人物造型代替。

提供 `PRO_CRIT.MSG`、中文映射 JSON 和含中文字形的字体后，人物阶段还生成 `elevation-<n>-floor-walls-doors-scenery-items-critters-labeled-zh-CN.png`。名称解析优先使用配置中明确列出的脚本文件名，例如 `Slappy.int → 斯来匹`、`Vance.int → 万斯`；没有覆盖时读取人物原型索引对应的 `PRO_CRIT.MSG` 名称，例如 `Harold → 哈罗德`、`Rutger → 罗格尔`。配置明确列为专名的角色显示“中文名 / English Name”，例如“哈罗德 / Harold”；警察、商人、贫民、农民、暴徒、男孩等通用类别仍只显示中文。这样既保留提取来源，又不会把复用通用原型的专名人物误标成职业。标签采用白字、深色底框、亮绿色细连接线，并按人物头顶位置进行碰撞避让；缺失 FRM 的人物仍按六角格锚点保留名称位置。

再提供 `PRO_ITEM.MSG` 和物品中文映射后，同一张标注图会为每个可见顶层物品增加黄色标签。普通物品显示名称；容器读取 MAP 中该对象的直接 `inventory`，逐项显示中文名称与数量，空容器明确标为“内含：空”。库存条目没有独立地图坐标，因此仍不绘制其 FRM，只作为所属容器的文字内容展示。人物标签优先布局，物品标签在共享的占位集合中继续避让，二者使用不同颜色的 1 像素连接线和边框。

### 知识库人物位置图后处理

人物资料页使用独立的“人物位置图”，不直接嵌入同时带人物、物品和容器清单的完整验收图。位置图以无标注完整合成图、人物透明层和人物标签元数据为只读输入；所有普通人物沿用渲染器实际使用的亮绿色 `(101, 231, 101)` 轮廓、引线和标签框，当前资料页人物则按地图对象 ID 选中，并改用橙色 `(255, 126, 48)`。选择焦点时必须使用 `object_id`，不能只按显示名匹配，以免普通人物重名或同一原型复用造成误标。

人物轮廓由人物透明层的非透明像素向外扩张后减去原始掩码得到，不覆盖人物自身像素。焦点人物再从其 `target_canvas` 附近选择最近的连通人物像素，使用 3 像素橙色轮廓覆盖普通绿色轮廓。标签文字、目标锚点和标签框分别复用元数据中的 `display_name`、`target_canvas` 与 `label_box_canvas`；人物页不绘制任何物品轮廓或物品标签。缺失 FRM 的人物仍保留名称锚点，但无法生成造型轮廓。

全部标注完成后再裁切活动区域，且必须保留未裁切派生图，避免以后更换焦点人物时重复生成基础地图。HUBOLDTN elevation 0 的完整画布为 `6656×3326`；哈罗德人物页使用原图坐标框 `(1750, 1000, 4650, 2450)`，得到 `2900×1450` 的活动区域图。旧城区区域总图使用 `(1750, 0, 4650, 2450)`，得到 `2900×2450`；它完整保留地图格0的对象 `25`、`26`、`27`，地图外交易库存箱 `28`、`163`，以及渲染器原有的锚点、引线和标签框。地图外状态仍在资料页表格中以警告或删除线说明。

裁切坐标属于“地图名＋楼层”的知识库展示参数，不是通用 MAP 坐标公式。处理其他地图时，应先从人物与物品锚点、建筑边界和标签框求取候选矩形，再目视确认没有裁掉活动道路、地图外对象、连接线或标签。最终 PNG 放入使用笔记附近的 `attachments/`，Obsidian 只嵌入裁切版；完整图继续作为可恢复来源保存。

最终合成把墙和门放回同一个对象队列：先 `OBJECT_FLAT`，再普通对象，各阶段按六角格编号和 MAP 源顺序递增。门独立层只画门，便于核对门洞；合成层不能简单地先画完所有墙再画门，否则跨格重叠时会破坏游戏遮挡顺序。

参考：[`proto_types.h`](https://github.com/alexbatalov/fallout1-ce/blob/0609bcfd0ec40ff0571d0f57fab2821eb461dc8b/src/game/proto_types.h)、[`protinst.cc`](https://github.com/alexbatalov/fallout1-ce/blob/0609bcfd0ec40ff0571d0f57fab2821eb461dc8b/src/game/protinst.cc)、[`art.cc`](https://github.com/alexbatalov/fallout1-ce/blob/0609bcfd0ec40ff0571d0f57fab2821eb461dc8b/src/game/art.cc)、[`anim.h`](https://github.com/alexbatalov/fallout1-ce/blob/0609bcfd0ec40ff0571d0f57fab2821eb461dc8b/src/game/anim.h)。

## 后续迭代

HUBOLDTN 当前尚未进入静态合成图的数据如下：

| 类型 | elevation 0 | elevation 1 | 合计 | 计划用途 |
|---|---:|---:|---:|---|
| 有效屋顶地砖 | 776 | 0 | 776 | 生成可独立开关的屋顶层，并提供带屋顶合成图 |
| 控制物件（`misc`） | 406 | 333 | 739 | 710 个 `block.frm` 阻挡格和 29 个出口格；只做调试覆盖层 |

推荐按以下顺序继续：

1. **屋顶**：按屋顶地砖坐标整体上移 96 像素，输出透明屋顶层和可选的完整合成图。资料地图默认可关闭屋顶，以免遮住室内人物和物件。
2. **阻挡格、出口格与脚本标记**：将不可见的 `misc` 控制对象转换为可选的彩色覆盖层，用于检查可通行区域、地图出口和脚本触发位置，不并入正常美术合成图。
3. **环境光与物件光源**：在全部坐标和遮挡层验收后加入地图环境亮度、对象光照范围及强度，避免把亮度差异误判为素材或坐标错误。
4. **扩展地图标注**：在已完成人物中文名的基础上，继续添加房间名、地点名、出口方向和任务相关物件标签，作为面向知识库的独立注释层。

完成屋顶后，离线静态地图主体即基本完整。脚本生成或移除对象、人物移动、战斗动画、门的实时开关、玩家周围半透明遮挡和屋顶动态隐藏属于“游戏时态图”，需要执行或模拟脚本与引擎状态，不能从 MAP 保存数据中直接还原。

每轮继续保留独立图层、统一坐标原点、确定性 PNG、元数据和校验文件，避免把坐标、素材、遮挡与光照问题混在一次调试中。

### 2026-07-30：人物标注阶段耗时复盘（53 分钟）

这 53 分钟是从需求分析到文档交付的端到端耗时，并不是图片渲染本身的耗时。两层地图在依赖已经缓存后，并行生成通常只需要约 6～12 秒；本次的大部分时间属于首次研发成本，包含：确认人物 FID、动画与武器变体的取图规则，建立 `MAP → prototype.list_index → PRO_CRIT.MSG` 的名称提取链路，按脚本文件名覆盖通用原型名称，核对中文译名，实现中文字体、标签避让和连接线，处理缺失人物素材，以及反复调整物品与人物的双重细轮廓。随后还执行了自动化测试、实际地图渲染、目视检查、确定性重跑和文档更新。

本次还暴露出两个容易浪费时间的工程问题：第一，`uv run --with .` 可能复用旧的本地构建产物，使运行结果没有包含工作区中的最新修改；后续开发态渲染应明确使用当前源码，例如设置 `PYTHONPATH=src`，或采用 editable 安装。第二，多个命令入口的参数块结构相似，宽泛补丁容易修改到非目标入口；后续应使用更精确的上下文修改，并尽早运行 Ruff、命令帮助和小范围测试来发现接线错误。

已经可以直接复用的成果包括：人物名称提取与脚本覆盖规则、中文译名配置格式、中文字体加载、确定性标签避让、缺图人物标注、物品与人物双重轮廓、元数据溯源和对应测试。后续处理同类地图时，不必重新研究这些机制，只需补充未覆盖的译名与脚本专名、并进行逐层目视验收。

建议采用以下快速流程：

1. 先提取目标地图中唯一的人物原名和脚本名，只处理尚未覆盖的译名。
2. 复用通用中文名称表，并用每张地图的小型配置文件记录专名覆盖。
3. 明确从当前工作区源码并行渲染各层，避免旧构建缓存。
4. 重点检查密集人物区、地图边缘、缺图人物、名称连接线，以及物品和人物轮廓是否同时保留。
5. 确定性重跑一次并核对 SHA-256，然后同步更新本文档。

因此，后续相同功能的地图会明显更快：同一张地图修改译名或样式后重新生成，机器执行通常不到 1 分钟；新地图若大部分名称已有译名，生成和检查通常可控制在数分钟到十几分钟。若出现大量新专名、特殊人物素材或新的渲染规则，耗时仍会主要落在译名核对、异常处理和人工目视验收上，不能只按渲染命令的秒级耗时估算。下一步还可把地图专用译名逐步沉淀为“通用译名表 + 地图覆盖表”，并增加批量渲染入口，进一步减少重复工作。
