# 统一资源索引设计草案

关联：[[项目导航]] · [[经验总结与待决策]] · [[工作计划 Checklist]]

## 目标

把 inventory、提取清单和各格式转换 JSON 合并为可增量重建的索引。索引只引用 `workspace/` 中的文件，不复制资源；同一路径的 DAT、松散覆盖和派生物都可追溯，失败也必须成为记录。

## 建议产物

| 文件 | 一行/一项代表什么 | 用途 |
|---|---|---|
| `index/resources.jsonl` | 一个来源资源 | 稳定主表，适合流式处理 |
| `index/derived.jsonl` | 一个派生文件 | 连接 JSON/CSV/PNG/WAV/MP4 |
| `index/failures.jsonl` | 一次失败或跳过 | 支持修复后定向重跑 |
| `index/collisions.csv` | 一个规范化路径及其全部候选来源 | 审核汉化/补丁覆盖 |
| `index/summary.json` | 类型、来源、状态和错误计数 | 批次验收 |
| `index/index.json.sha256` | 上述索引文件的组合清单哈希 | 判断索引是否完整变化 |

## 资源主记录

每条 `resources.jsonl` 至少包含：

```json
{
  "resource_id": "sha256:稳定身份摘要",
  "source_kind": "dat1|loose",
  "source_name": "MASTER.DAT|CRITTER.DAT|DATA",
  "internal_path": "TEXT/ENGLISH/DIALOG/HAROLD.MSG",
  "normalized_path": "text/english/dialog/harold.msg",
  "resource_type": "text",
  "extension": ".MSG",
  "size": 13176,
  "sha256": "...",
  "extraction": {"status": "extracted", "path": "raw/master/..."},
  "conversion": {"status": "converted", "format": "msg", "schema_version": 1},
  "effective_source": false,
  "warnings": []
}
```

`resource_id` 不应依赖本机绝对路径。建议对 `source_kind + source_name + internal_path` 的 UTF-8 规范串计算 SHA-256；内容哈希单独保存，因为松散覆盖可能同路径不同内容。

## 派生记录

`derived.jsonl` 一项对应一个实际文件：

- `resource_id`：反向连接唯一来源。
- `role`：`metadata_json`、`csv`、`png_frame`、`wav`、`preview_mp4` 等。
- `relative_path`：相对 `workspace/`，禁止绝对路径。
- `size`、`sha256`。
- `generator`、`generator_version`、`schema_version`。
- `lossless_from_source`：布尔值；MVE 预览 MP4 必须为 `false`。
- `validation`：结构校验、人工抽查及时间。

## 状态模型

提取与转换状态使用固定枚举，不用自由文本：

- `not_selected`
- `planned`
- `extracted`
- `converted`
- `skipped`
- `unsupported`
- `failed`
- `stale`

当源大小、mtime、内容哈希、生成器版本或输出哈希变化时，旧转换标为 `stale`，不要直接删除历史失败原因。

## 来源优先级与冲突

规范化路径只用于发现冲突，不作为唯一身份。候选来源全部写入 `collisions.csv`，字段至少包括：规范路径、来源、原始大小写路径、大小、哈希、是否内容相同、建议有效来源和决策依据。

默认优先级可暂定为松散 `DATA/` 高于 DAT，但必须满足：

1. 规则显式写入索引配置。
2. 被覆盖记录仍保留。
3. 不同大小写路径不得在 Windows 上写入同一目标目录。
4. 无法判定补丁/汉化来源时，`effective_source` 留空并进入人工审核。

## 批次与恢复

每次运行生成 `batch_id`，建议使用 UTC 时间加配置摘要。批次清单记录输入清单哈希、选择器、程序提交、Python/FFmpeg 版本、开始/结束时间和错误数。

写入顺序：

1. 读取并验证所有输入清单。
2. 生成完整计划，不写最终索引。
3. 将 JSONL/CSV 写入同目录临时文件。
4. 逐文件计算哈希并做交叉引用检查。
5. 全部通过后原子替换整组索引，并最后写组合哈希。

中断后重新运行应根据输入哈希和现有派生文件哈希复用成功项；不能只凭“文件存在”判定成功。

## 最小实现顺序

1. [x] 只合并现有 `inventory.json`，生成 `resources.jsonl` 与冲突报告。
2. [x] 接入 extraction manifests，补资源内容哈希和 `extracted` 状态。
3. [x] 接入 MSG、INT、FRM、MAP、ACM、MVE 的元数据 JSON，生成派生记录。
4. [x] 加入失败清单、stale 检测和组合哈希。
5. [x] 用当前代表样本做回归；尚未开始下一批按类型提取。

验收标准：任何派生文件都能连接到唯一来源；任何冲突都不静默覆盖；删除整个 `index/` 后可以从现有清单和元数据完全重建。

## 第一阶段实测（2026-07-27）

- 生成 26,111 条来源资源记录。
- 发现 765 个不区分大小写的冲突路径，共 1,530 个候选来源；全部保留为待审核，未自动选择覆盖来源。
- `resources.jsonl`、`collisions.csv`、`summary.json` 和组合校验清单共约 14.8 MiB，只写入代码工程的 `workspace/index/`。
- 连续两次生成的组合校验清单 SHA-256 一致，证明当前输入下输出可重复。
- 接入 10 份提取清单：4,326 条结果合并为 4,324 个资源，2 条重复一致，0 条 stale。
- 接入 9 份转换元数据：99 个输出文件全部进入 `derived.jsonl`，0 条 stale，`failures.jsonl` 为空。
- 0.2.0 内容寻址批次 ID 为 `sha256:fbe4a2c2a8e8021a90b14c5966e054713999bcc2ab6cc5d8b1abfe385855f9dd`。
- 自动测试为 121 项通过、7 项因 Windows 符号链接权限跳过。
